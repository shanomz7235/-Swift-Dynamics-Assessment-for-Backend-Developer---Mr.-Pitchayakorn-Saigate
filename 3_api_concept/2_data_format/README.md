# JSON vs Protocol Buffers (Protobuf)

ทั้งสองอย่างคือ "รูปแบบการแปลงข้อมูลให้ส่งผ่านเครือข่ายหรือเก็บลงไฟล์ได้" (serialization) แต่ออกแบบมาคนละแนวทาง

- **JSON** เน้นให้คนอ่านออก และใช้งานง่าย
- **Protobuf** เน้นให้เล็ก เร็ว และมีโครงสร้างข้อมูลที่ชัดเจน

## JSON คืออะไร

JSON (JavaScript Object Notation) คือข้อมูลที่เขียนเป็นข้อความ (text) อ่านได้ด้วยตาเปล่า

```json
{
  "id": 1,
  "name": "Sheesh",
  "active": true
}
```

## Protocol Buffers คืออะไร

Protobuf คือรูปแบบข้อมูลของ Google ที่แปลงข้อมูลเป็น **ไบนารี (binary)** ก่อนส่ง โดยต้องเขียนไฟล์โครงสร้างข้อมูล (schema) ชื่อ `.proto` ก่อน

```proto
syntax = "proto3";

message User {
  int32 id = 1;
  string name = 2;
  bool active = 3;
}
```

จากนั้นใช้เครื่องมือ `protoc` สร้างโค้ดสำหรับภาษาที่ใช้ออกมาให้ แล้วเรียกใช้ผ่านโค้ดที่สร้างขึ้น

ตัวเลข `1`, `2`, `3` คือ Tag Number ที่ใช้ระบุตำแหน่งของข้อมูลแทนการส่งชื่อฟิลด์ที่เป็นข้อความยาวๆ

## ความแตกต่างหลัก ๆ

### 1. รูปแบบข้อมูล
- JSON: เป็นข้อความ เปิดอ่านได้ทันที
- Protobuf: เป็นไบนารี เปิดดูตรง ๆ แล้วอ่านไม่ออก ต้องใช้เครื่องมือถอดรหัส

### 2. Schema (โครงสร้างข้อมูล)
- JSON: ไม่บังคับ จะส่งอะไรมาก็ได้ (ถ้าอยากมี schema ต้องใช้ JSON Schema เพิ่มเอง)
- Protobuf: บังคับต้องมีไฟล์ `.proto` เป็นข้อตกลงร่วมกันระหว่างผู้ส่งและผู้รับ

### 3. ขนาดข้อมูล
- JSON: ใหญ่กว่า เพราะต้องส่งชื่อฟิลด์ทุกครั้ง และเลขต้องเขียนเป็นตัวอักษร
- Protobuf: เล็กกว่ามาก (มักเล็กกว่า JSON หลายเท่า ขึ้นกับลักษณะข้อมูล)

### 4. ความเร็ว
- JSON: แปลงข้อมูลช้ากว่า
- Protobuf: แปลงข้อมูลเร็วกว่า ใช้ CPU น้อยกว่า

### 5. ชนิดข้อมูล
- JSON: มีชนิดพื้นฐานน้อย (string, number, boolean, array, object, null) ไม่มีชนิดวันที่โดยตรง และเลขทุกชนิดรวมเป็น number
- Protobuf: มีชนิดละเอียด เช่น int32, int64, float, double, bytes และมี enum

### 6. การเปลี่ยนแปลงโครงสร้างในอนาคต
- JSON: เพิ่มฟิลด์ได้ง่าย แต่ไม่มีกลไกตรวจว่าใครเปลี่ยนอะไร ต้องคุยกันเอง
- Protobuf: รองรับการเพิ่มฟิลด์ใหม่โดยไม่ทำให้ระบบเก่าพัง ถ้าทำตามกติกา (เช่น ห้ามเปลี่ยนหมายเลขฟิลด์เดิม)


## ข้อดีและข้อเสียของ JSON

### ข้อดี
- **อ่านง่าย** เปิดดูแล้วเข้าใจได้ทันที ช่วยให้ debug ง่ายมาก
- **ใช้งานง่าย** แทบทุกภาษาและทุกเครื่องมือรองรับ
- **เบราว์เซอร์รองรับในตัว** เหมาะกับ Web API และ Frontend
- **ไม่ต้องตั้งค่าอะไรเพิ่ม** ไม่ต้องเขียน schema หรือสร้างโค้ดก่อน
- **ทดสอบง่าย** ใช้ Postman, curl หรือเบราว์เซอร์ยิงทดสอบได้เลย

### ข้อเสีย
- **ขนาดใหญ่** ส่งชื่อฟิลด์ซ้ำทุกครั้ง เปลืองแบนด์วิดท์
- **ช้ากว่า** เพราะต้องแปลงข้อความเป็นข้อมูลและกลับกัน
- **ไม่มีการบังคับโครงสร้าง** ฝั่งส่งอาจส่งผิดชนิด หรือลืมฟิลด์ได้ จึงต้องตรวจสอบเองในโค้ด
- **ชนิดข้อมูลไม่ละเอียด** เช่น เลขจำนวนเต็มขนาดใหญ่มาก (int64) อาจเพี้ยนในบางภาษา เช่น JavaScript
- **ไม่มีที่สำหรับคอมเมนต์** ในมาตรฐาน JSON

## ข้อดีและข้อเสียของ Protobuf

### ข้อดี
- **ขนาดเล็ก** ประหยัดแบนด์วิดท์และพื้นที่เก็บข้อมูล
- **เร็ว** แปลงข้อมูลเร็ว เหมาะกับระบบที่รับส่งข้อมูลจำนวนมาก
- **มี schema ชัดเจน** ทั้งสองฝั่งตกลงโครงสร้างตรงกัน ลดข้อผิดพลาดจากการส่งข้อมูลผิดชนิด
- **สร้างโค้ดให้อัตโนมัติ** ได้ struct/class พร้อมใช้ในหลายภาษา ไม่ต้องเขียน parsing เอง
- **รองรับการเปลี่ยนแปลงในอนาคต** (backward/forward compatibility)
- **เป็นพื้นฐานของ gRPC** ซึ่งนิยมใช้สื่อสารระหว่าง microservices

### ข้อเสีย
- **อ่านไม่ได้ด้วยตาเปล่า** debug ยากกว่า ต้องใช้เครื่องมือช่วย
- **ต้องมีขั้นตอนเพิ่ม** เขียนไฟล์ `.proto` และรัน `protoc` ก่อนใช้งาน
- **เรียนรู้เพิ่ม** ทีมต้องเข้าใจกติกา เช่น การจัดการหมายเลขฟิลด์
- **ไม่เหมาะกับเบราว์เซอร์โดยตรง** ต้องมีตัวช่วยเพิ่ม (เช่น gRPC-Web) ทำให้ใช้กับ Frontend ยุ่งยากกว่า
- **ต้องมี schema ทั้งสองฝั่ง** ถ้าไฟล์ `.proto` ไม่ตรงกัน ข้อมูลจะถูกตีความผิด
- **ทดสอบยากกว่า** ใช้ curl หรือ Postman ธรรมดายิงตรง ๆ ไม่ได้
